# 🏛️ Architecture — Rise of Git

How the code is organised. For the game rules themselves (XP, levels, districts, resources, designs) see [GAME_GUIDE.md](GAME_GUIDE.md).

---

## Technology Stack

* **3D:** Three.js + React Three Fiber + @react-three/drei
* **Frontend:** React 19, Vite, TypeScript
* **UI:** Tailwind CSS v4 (via `@tailwindcss/postcss`, configured in `src/index.css`) + Lucide icons
* **Backend:** Express 5 run with `tsx`
* **Storage:** SQLite via `better-sqlite3` (WAL mode), file at `server/data/realm.db`
* **Data source:** Git REST API (token) + Git OAuth2 for sign-in
* **Audio:** Web Audio API, procedural sounds (`useSound.ts`)

Scripts: `npm run check:models` (fails on z-fighting / flickering faces in NPC models, in Normal and in HD (the HD model kit's HD-only parts and HD shapes), every rising / crumbling step of the epic landmarks, boss rigs at rest, the actors' HD models and every world-map castle stage in Normal and HD, `scripts/check-models.ts`), `npm run sim:leaderboard` (Hall of Renown worked examples and period windows; exits 1 if their order changes), `npm run backfill:leaderboard` (rebuild `dev_daily_stats` by hand), `npm run sim:balance` (with `scripts/mercSim.ts`, which measures each mercenary band's power and calibrates its soldier-equivalents, and `scripts/armorySim.ts`, which measures each Armory set's power and the scale that puts it on target; `scripts/championSim.ts`, which measures a champion's worth and finds the strongest kit it can roll; stat sheet, buffs/debuffs; live-engine checks with real armies: Voidrift, duel, PvP chart, gathering income vs harvest, rally vs swarm (rallies fight `COMBAT.RALLY_MAX_ROUNDS`), bosses (rallies, a rally vs the same marches apart, Vengeance stacks, and one ruler's every march slot by title profile), NPC kingdoms & recovery (Nethergarde attackers included), Overseer's Resolve, army sizes & rebuild time, plunder, walls & sieges, burning, mob / bandit tiers (all five civilizations), world disasters (Blood Moon boss rallies, Tempest losses vs rations, a year of the schedule, client mirror), mercenaries, the Armory (each set's power, its worth in soldiers, the PvP chart with every civilization fully equipped, and every PvE ceiling with a ruler in their best set: packs, free realms, full frontier gates, bosses), champions (a max-level champion's march at most +25%, and every PvE ceiling with a champion leading the ruler's first march); with a TWEAKS block (incl. `titles`: stat buffs on every attacking army) → BALANCED/UNBALANCED, exit 1 when unbalanced, `scripts/sim-balance.ts`), `npm run sim:arts` (Battle Arts on the live engine: each Art's worth over a 6-round drill duel against the power budget ±15%, Finales and Instincts, the drill kits' curve common → mythic and the ladder gap, kit sizes, deterministic replays, the client mirror → BALANCED/UNBALANCED, exit 1, `scripts/sim-arts.ts`), `npm run sim:population` (growth per civ from genesis and after a war, `scripts/sim-population.ts`), `npm run sim:war` (balance table: live-battle assaults a developer of each civ/City Hall level, filling every march slot, needs to break an NPC void kingdom, `scripts/sim-war.ts`), `npm run sim:gates` (frontier gates: a lone City Hall 15 ruler of each civ against each bare gate, its losses, the waves it takes to set the gate burning, and against a gate filled to its reinforce cap, `scripts/sim-gates.ts`), `npm run disaster -- <kind> [minutes] | end | list` (calls a world disaster on the local realm without signing in; the running server raises the notices, `scripts/call-disaster.ts`), `npm run sim:scouting` (Spies & Counterspies odds: true report / caught / deceived by party size, Lantern Streets and Spymaster's Tower tiers on both sides, elves, a full frontier gate; exits 1 if success leaves 50–95%, `scripts/sim-scouting.ts`), `npm run dev` (server in `tsx watch` mode, so it restarts on server code changes, + Vite together), `npm run build`, `npm run lint` (ESLint across `src/`, `server/src/` and `scripts/` with TypeScript validation on client (incl. scripts) and server), `npm start` (server, also serves `dist/`).

## Data Flow

```
Git API ──► realmBuilder.buildRealmFromGit()        every GIT_SYNC_INTERVAL_HOURS (min 1 h) + on start
                 │  users, emails, repos, commits, PRs, reviews, subscriptions
                 ▼
             db.saveGitSnapshot()  ──► SQLite
                 │
                 ▼
             titles.rebuildRealmWithTitles()             milestone titles → user_earned_titles, then the kingdoms
                 │
                 ▼
             db.getAllKingdomsFromDB()                   XP (scoring.ts), levels & districts (kingdomUtils.ts),
                 │                                       saved city plan (kingdom_layout)
                 ▼
             in-memory `kingdoms[]` (routes.ts) ──► REST /api ──► useGameState ──► Scene3D / UI

syncService clock (every SYNC_INTERVAL_MINUTES) ──► db.executeResourceAllocation(kingdoms) ──► SQLite + ledger
                                                    (+ demographics: births, deaths, upkeep; NPC garrison regen)

war tick (every 2 s + on GET /marches) ──► warEngine.runWarTick ──► combat.stepBattleRound ──► SQLite
                                           (arrived marches → live battles / scout reports, casualties, civ swaps,
                                            mob packs' shared losses; in-memory kingdoms + Voidrift slots refreshed)

REST reads are per viewer: fogKingdomsFor / fogSpiresFor / getRovingSpawnsFor hide other civilizations' numbers
(and mob / treasure details) from the signed-in session user, unless one of their scout reports covers it.
```

The Git refresh and the harvest are **independent**: refreshing data never pays resources. The harvest clock reads its last run time from SQLite so restarts don't double-pay.

## Key Design Decisions

* **Server is the source of truth for game rules.** XP, levels, prestige, districts and plot slots are computed server-side and sent to the client; the client only decides *how* to draw a given level.
* **Realm time is shared, the sky is local.** `realmTime.ts` (server) decides whether the harvest window is day or night (alternating per harvest) and the season, for the harvest, births and marches, and sends the window and season on `/status`. Each browser works out the sky's hour from how far the window has run (`useRealmClock`), so the sky moves on between polls; the light changes in half-hour steps of the realm day (the static shadow map is redrawn only then), and season tints rebuild part colours once a week. Weather and clouds are two instanced layers that never cast shadows; a world disaster adds one more (and the Blood Moon's moon), tints the lights in RealmSky and the terrain / grass colours through `skyState.skyWeather.disaster`. Its rules are on the server only (`disasterRules.ts`), read where harvest, births, deaths, march launch and battle rounds are computed; a Blood Moon is checked per round at the round's time, so only rounds inside its window feel it.
* **Deterministic visuals.** Every plot uses a seeded RNG keyed by the plot, so a building looks the same on every load and only changes when its level/state changes.
* **Stable city plan.** `kingdom_layout` stores each repo's district + slot so buildings never jump around between syncs; only the owner swapping two buildings' plots changes it. New repos take over vacant plots of removed repos.
* **One draw call per primitive.** City geometry is emitted as flat part lists by `blueprints.ts` and rendered through `InstancedParts`; moving things go through `Actors` with LOD. World-map castles work the same way: `castleParts.ts` lists each civ's castle and `WorldCastles` merges each style's parts into one geometry per (opacity, sidedness, shadow flags, animation) and draws it with one instance per castle. Part colour, hover colour, roughness, metalness, emissive and stage range are vertex attributes read by a patched `MeshStandardMaterial` (and a matching shadow depth material), so parts outside a castle's stage collapse in the vertex shader. Each batch is indexed (vertices equal in every attribute shared, bit for bit), so the vertex shader runs once per shared corner, not once per triangle corner: in HD a batch is about a quarter of its unindexed vertices, which took the HD castles from 5.4 to ~2 ms on the dev laptop. In HD each batch is also split by the stages in use (a draw per stage, only that stage's parts), so a castle no longer runs the vertices of other stages: −0.5–0.9 ms more where several castles are in view, for ~+28 draws at the overview. Normal stays one batch with stages collapsed in the shader. Every castle on the map costs ~41 draw calls in all, however many there are.
* **One rarity ladder, one effect kit.** Rarity is styled the same everywhere (docs/MODEL_STYLE.md *Visual rarity ladder*). `TierFx` draws every rare+ thing in a view in at most three draw calls (an open-cylinder curtain of light standing round the structure, beam column, one points cloud whose vertex shader runs embers, orbiting motes and glints); nothing is drawn as a ground disc. `fxTierOf(rarity)` maps NPCs onto it, Wonder castles and red-star plots (`RED_STAR_FROM` in utils/castle.ts) are legendary, the Empyrean and Celestial plots mythical, and the city gate / fountain / dragon / spire follow their improvement tier (`IMPROVEMENT_FX` in blueprints.ts: 3 rare, 4 epic, 5 legendary). Bosses keep their rig's own `BossFx`.
* **Living models at no draw-call cost.** Part motion runs in the `InstancedParts` vertex shader from per-instance attributes (anchor, kind, phase, tempo, size). `buildNPCModel` seeds every authored part cycle from the NPC's id, makes glowing parts of structures pulse (structures never move as a whole) and gives the wreck its rocking (`Part.model`, a second anchor + cycle applied after the part's own, so a fluttering sail still rocks with its hull). The world map draws every Builder-modelled roving spawn, buffer realm, epic / legendary landmark and frontier gate through one batch (`npcModelParts` in FlatWorldMap3D): draw calls grow with distinct shapes, not with landmarks on the map (a rotation day's 4 per region cost nothing extra); each spawn gets a seeded whole-model idle (`wholeModelIdles`, shared with NPCModel), in a site only the living things breathe (`Part.breath`), and the wreck keeps the rocking its model brings.
* **Motion kit (walkers on the GPU).** A walker's body and every part riding it work out the same pose from time and the walker's tempo alone (`walkPose` in the `InstancedParts` shader): stride phase, footfall dips, lean from speeding up / braking, weight over the supporting leg, hip twist, the turn round its loop, and in its seeded 3–5 s pauses breath, glances and one idle event (a biped, marked `sub` 0.25 on its walk cycle, stands upright and stretches or looks down where a beast shakes itself or sniffs). Parts declare a role (`Builder.add` options `arm`, `head`, `torso`, `trail`; idle kinds 17 with amp ±2, 19, 20, 21): the head undoes the body's lean, roll and twist about its neck and glances; a torso and arms turn against the hips about the model's ground point (passed to the part's cycle as `axis`); a trail evaluates the pose `lag` seconds earlier and rotates by the difference (a spring in closed form). Flyers' wings beat with a power stroke (`wingPos`) and the body heaves in time (the wingbeat rate rides in the walker cycle's `sub`, packed into the kind attribute's fraction, as does a trail's lag). No per-creature CPU work and no new draw calls. Batched NPCs no longer grow on hover (their hover card still shows).
* **HD castles (the merged pipeline).** `WorldCastles` merges each castle style's parts into one geometry per batch key, so HD there is a second set of batches with the same keys: every part drawn through its HD twin (`castleGeometry(key, true)`: a bevelled box, chamfered towers with more segments, rounder domes; four- to six-sided roofs and towers keep their facets) and the HD-only detail of `castleHd.ts` merged in, while Normal-only parts (`hd: false`) drop out. The kit's surface shader (`KIT_FRAGMENT_*` from `InstancedParts`) reads per-vertex values packed four to an attribute (a vertex shader takes at most 16): material and seed, the part's own space and size, its ground for soft AO, its courses (dressed stone on upright faces, overlapping roof tiles, both faded by screen size) and the cloth or smoke motion; the castle's stage and hover share one instance attribute in HD. Draw calls stay as in Normal (+1 where a civ gains a batch key it lacked); the cost is vertices, since every castle runs all of its civ's parts and collapses those outside its stage, so castle detail takes a lighter geometry than a creature's (`twinOf`: a plain box for anything small, the plain cylinder, cone or ball for anything tiny). `check:models` checks every castle stage in Normal and HD. The Wonder's HD layer (legendary) lives in the same part lists at `minStage: 4`; because every castle runs all of its civ's parts through the vertex shader, those parts go into batch keys of their own (`wonder`) drawn only on Wonder castles, so a map of Keeps never pays for them (2–3 draws per civilization that has a Wonder on the map). Normal parts the Wonder's HD version replaces carry `hdMaxStage` (their last stage in HD). Two more GPU motions ride the HD batches: `turn` (round an upright axis, its normal turned too) and `pulse` (a glow swelling and fading), from Builder `idle: spin` / `idle: pulse`.
* **HD city (a tagged scene).** The city's improvements, its forest ring and every plot (pad, structures, dressing; vacant plots too) are built on builders with `kit` set, so their parts carry `Part.kit`; `InstancedParts kit="tagged"` (the city view in HD, the Codex's improvement and building previews) draws them through the model kit and anything untagged (the mourning props of a punishment) exactly as always. Tagged glows stay plain (they share the scene's glow batches), and a tagged box far longer than it is thick (a wall, a road, a kerb) is drawn as a `slab` (a plain box in HD too) so its bevel doesn't stretch. `Builder.mat` gives everything a builder adds a default material. The kit's `masonry` surface lays courses round a part's sides (by angle on a cylinder) and flagstones on its top; `tiles` lays overlapping rows down a roof, staggered along each facet's own eaves (taken from the facet normal by screen derivatives, since a prism's or pyramid's vertex normals bend round its eaves). Each civilization's drawers (`<civ>Structures.ts`) tag every Normal part with its material and add HD-only detail by tier through the structure kit's helpers (`win`, `door`, `chimney`, `vane`, `circling`, `bale`, `lampPost`, `pennant`) and their own; HD parts never draw on the plot's rng. The scene's `detail` list (flowers, weeds, crates, barrels, sacks, carts, cradles) is drawn with `kit="tagged"` too, hidden past the LOD distance like the rest of it; its HD-only parts carry `detail: true`. Draws at the city's default view: HD 51 with the models on, 40 off (the plots' parts move into the kit batches the improvements already had). Zoomed in, the heaviest kit batches draw only their chunks in view (`InstancedParts chunk`, 24 units across): the Archon's 50 Celestial plots go from 3.4M to ~0.8M triangles closest over the hall, for up to ~30 more draws; reordering the instances themselves (as the map's `cull` does) would upload megabytes a frame on the move, which stalls an integrated GPU for tens of ms.
* **HD actors (their own pipeline).** People, animals and moving building parts are drawn through `Actors`, which poses every agent on the CPU each frame. Their HD versions (`actorHd.ts`, feature `actors`) are separate part lists in the actor's own frame, built with the Builder and the model kit (Normal keeps its templates untouched). `ActorsHd` draws every kind together with one mesh per shape kind (its parts of every kind in a part texture, instanced by count); per frame the CPU writes one row per on-screen agent into one float texture (its matrix, stride, action, biped flag and colour slots), packed kind after kind, and gives each mesh the runs of the kinds with someone on screen, so its instance count is the visible agents × parts summed over them: off-screen agents cost nothing on the GPU, a shape no visible kind uses issues no draw, and draws grow with shape kinds, not with actor kinds. The part motion (stepping legs, swinging arms, the body's dip, lean and roll, the shoulders' counter-turn, a steady glancing head, trailing hair, robes and tails, beating and folding wings) runs in the vertex shader from the part's role and pivot; the fragment shader is the HD model kit's. Parts take the full HD twin from 0.3 across, the light twin below and a coarse twin under 0.1, since many agents stand on screen at once. Measured at the city's default view: 79 draws close in vs 35 for Normal (each new shape kind and the HD twin sizes are draws of their own) and ~+250k triangles, GPU inside the noise; zoomed in on the map +12 draws and ~+83k triangles, GPU inside the noise.
* **HD model kit (one model, two renderings).** A Builder model's part list is its only definition. Normal draws it as always; HD (feature `models`, `InstancedParts kit`) draws the same parts through shared HD geometry twins (bevelled, rounded, more segments) or a part's `hdShape`, with per-part materials as instance attributes, surfaces and bump in the fragment shader, soft AO, HD-only detail parts (`hd: true`) in place of Normal-only ones (`hd: false`) and seeded relaxed rest poses (`pose`, written into the instance matrix once). Everything stays instanced: draw calls grow only with the new shape kinds a model uses (+3 at the map's closest zoom); motion stays on the GPU. `animateParts` seeds Normal parts by their place among Normal parts and `separateCoplanar` never moves a Normal part for an HD one, so HD detail never changes Normal (a part-by-part diff of every model against the previous build is identical). The `figure` and `beast` kits in `spawnModels.ts` tag their parts, so every creature built from them gets its HD version; the pilots (wolf pack, highwayman, goblins, trolls, magma golem) and every other roving band adds HD-only detail by tier. The figure kit's HD `face` (eyeballs under lids, brow, nose, mouth on a chin, ears; a `beast` face for snouted folk; a `skull` face) replaces the two square eyes; `faceAt` puts that face on another head (a harpy's); `allMat` makes a whole figure one material (a petrified statue); `hood`, `pouch`, `crossbow`, `scimitar`, `roundShield` (on the left forearm) and `lanternFrame` are shared HD props. Small and thin HD parts use a lighter twin of their shape (a second batch per shape), since most kit parts ride walkers and every vertex works out its walk. Tails in HD are chains of overlapping capsules (`tail` in `kitParts.ts`): every segment is a trail part with the same root and a growing lag, and the standing wag's phase follows the lag, so a tail bends and ripples instead of swinging stiff. HD weapons are gripped: `along` lays a part between two points, `fist(side)` is where a figure's hand closes, and `sword` / `spear` / `club` build HD weapons through it. Resource nodes and treasures (`buildSpawnModel` in `npcs.ts`) get theirs through the same kit, with `humanoid`, `quadruped` and `chest` tagging their parts (a chest's fittings climb with its tier). HD detail on a swaying Normal part takes its `sync` number (`Part.sync`): `animateParts` gives the whole group the first part's idle, so wheat ears and grape bunches bend with their clump or vine. Foliage and crops use the `leaf` surface. The wild sights (`NPC_KINDS`) get theirs the same way: `stackedArc` hands each swaying segment of a kraken's tentacles or a sandworm's coils to a rider that adds synced HD parts (a capsule along the arc, so the beads read as one limb; suckers, scutes), and `faceAt` (exported from `spawnModels.ts`) gives the mermaid and the yeti a face. The hand-tuned sights (`HAND_TUNED_NPCS`) still draw a model each, so every shape kind their HD version adds costs a draw per copy: they keep to the kinds they already use plus one or two (the kraken only spheres and capsules). The free realms (`realms.ts`, every stage), the frontier gates (`gates.ts`) and the 24 epic landmarks (`landmarks.ts`) get theirs the same way (the four legendary landmarks keep the kit baseline: they are to be hand-built heroes); their rising, crumbling and broken-open models are generated from the part list with Normal parts seeded by their place among the Normal parts (`partSeeds` in `landmarkStages.ts`), so HD detail never changes those either.
* **Batched heroes.** One-of-a-kind sights whose HD version is hand-built (the legendary landmarks, the Nethergarde Core, the legendary sites) are not a component each: their builders put parts into a shared set of hero materials, and on the map `HeroBatch` merges every hero's parts per material into one mesh, so the batch costs one draw per material (4: matte, metal, glow, cloth, the look carried by surface kinds) plus one for sparks and four for the auras, however many heroes stand. Motion rides on the GPU per vertex (`Kit` with `motion`), so moving parts merge with static ones; parts keep their own index so shared corners are shaded once (the map is bound by vertices on the dev laptop), and with no hero in view the batch draws nothing (each hero's reach is a sphere; the shadow pass still gets them all). Heroes with CPU motion (the Empyrean's chains) stay components; `HeroMount` compiles both kinds behind the loader.
* **Rigged heroes (world bosses).** A boss needs CPU motion (keyed actions with holds, events, springs, turning on its attackers), but a component with a draw per part would undo what the hero kit bought. So bosses are built on the same kit and the four shared hero materials, every part inside a bone (`aBone`, the model built at rest, each bone a pivot and a frame); each frame `RigPlayer` poses every boss in view on the CPU (on the map a boss out of view keeps its pose; back in view it plays its last 0.4 s first, so a blend or spring settles unseen) and writes one 3×4 matrix (plus ghost, glow and the root's time since an impact) per bone into one float texture, which the materials read after the kit's GPU motion. All bosses on the map are one `BossBatch`: 4 material draws, sparks, bursts and embers (7 draws) however many bosses and bones; a slumbering boss is collapsed out of the opaque draws and drawn by a ghost material (4 more draws while one slumbers). Nothing in it casts shadows. A new boss is a new `BossHeroDef` on the same runtime.
* **Static shadows.** Both views use `useStaticShadows`, which redraws the shadow map only when the scene changes; anything that moves casts no shadow (townsfolk get a shared blob shadow instead). The town hall is merged by `MergeStatic` into a few meshes; animated parts are marked `DYNAMIC` and left alone. The canvas pixel ratio is capped at 1.5.
* **World build behind a loader.** Building the continent (terrain mesh, NPCs, scatter) blocks the page for a few hundred ms, so `FlatWorldMap3D` shows a CSS-spinner loader first and builds right after it paints. The built world is cached per world map, and so are the NPC part lists built from it and the water's depth samples, so returning from a city builds none of them again; after a sync the old map stays up while the new one builds. The city view works the same way: `Scene3D` keeps a "Raising the kingdom…" loader up from the click (including fetching a different kingdom) until `CityView3D` has mounted its meshes after the loader painted and drawn its first frames. Both views' content sits in a `CompileGate`: hidden until its shader programs have linked in parallel, so no frame stalls on a link (the loader, and the labels with it, waits meanwhile; coming back to the map shows the loader too).
* **Build chunks.** `vite.config.ts` splits the bundle into long-lived files: `three`, `r3f`, `react`, `world` (everything in `components/3d/world/` the map needs at startup) and the app (`index`), so a UI change doesn't make players re-download the models or the 3D engine. The Royal Codex and the login screen are lazy chunks loaded on first use; Xal'Vorath's HD showcase (`HighGraphicsSingularity`) is a chunk of its own that both the Codex and the login screen load (the login screen also loads the HD hero models). The HD hero models (the hero kit, `heroes.ts`, the `hero*` bosses, creatures, mercs and sites, `HeroBatch`, `BossBatch`, `HeroMount`, `bossParts`, `HighGraphicsEmpyrean`) are left out of `world` and reached only through `hdModels.ts`, which `hdModelsLoader.ts` imports dynamically when HD is on (at start in HD, or behind "Applying graphics…" on the switch), so Normal never downloads them; the Codex shares that chunk. Never import these files statically from code the map or city loads (types are fine), or they ride along with the page. Don't give them a `codeSplitting` group of their own either: a group also captures its modules' dependencies (React, the icons) and loads with the page. Keep the 900 kB `chunkSizeWarningLimit`: when a chunk passes it, split it or load it lazily rather than raising the limit.
* **Emoji are drawn as line icons, in one place.** Text all over the UI (and from the server: notices, NPC names, gem and civ emblems) carries emoji; the wrapped JSX runtime (`src/jsx`) turns every one the map in `glyphs.tsx` knows into its lucide icon when the element is created, so no render site has to. One type check per element, a regex only on strings; the bundle keeps only the icons the map names. Every picker is a `Combobox` (no native `<select>`, whose options can't hold an icon).
* **Commits are never deleted**, so XP keeps accumulating beyond the lookback window.
* **Deeds are XP rows, not commits.** The Scriptorium's sealed deeds are read by `getAllKingdomsFromDB` next to commits, PRs and reviews: their XP lands on the repo (a deed-only repo becomes a building), counts in the past-week XP that weights the harvest (`activity.weekDeedXp`) and in `xpBySource`, but never in the commit quota or the Hall of Renown's `dev_daily_stats`. The deed tables are created in `initDB` so every script that builds kingdoms has them; the rules live in `scriptorium.ts`.
* **Nethergarde Voidrift & Special Overseers.** Managers and trackers listed in `SPECIAL_USERS` are permanently bound to Nethergarde Voidrift (`arcane`) as max-level overseers (Lv25 Wonder, Prestige 4, all 10 improvements maxed including Tier 5 Citadel Ramparts, 20 honorary Lv25 buildings across districts if repo-less with 35/25/25/15 ratio, 365 streak liveliness, excluded from recurring harvest distributions). Other developers are balanced evenly across the 4 normal civs ($B$ each) with division remainders joining the Voidrift.
* **The Archon of the Realm.** `ARCHON_USERS` logins are folded into `config.specialUsers`, so every overseer rule (Nethergarde, maxed improvements, `resetOverseers`, harvest exclusion, no marches, no titles, decree powers) applies with no extra checks; `config.archonUsers` / `isArchonUser` / `kingdom.isArchon` mark the differences: `getAllKingdomsFromDB` builds castle Lv30 and 50 Lv30 buildings (`ARCHON_*` in kingdomUtils.ts, honorary halls fill the rest), `planMarch` refuses attacks, rallies and scouts on them, decrees refuse to shield or punish them, `resetOverseers` respawns them at City Hall 30. `getOrGenerateFlatWorldMap` pins the Archon's castle to the Voidrift's centre (other castles are moved off that seat) and serves the Nethergarde Core as `ruins-ascended` (floating over it) while an Archon is seated. The client draws castle stage 5 (Empyrean) from `EMPYREAN_PARTS` / `EmpyreanHall` and Lv26+ plots with a Tier 4 Celestial structure.
* **Battle Arts are data on the stacks.** A named unit's kit is a `UnitKit` of ids (battleArts.ts) set as `kit` on a `LiveAttackerStack` or on the `LiveDefenderState` garrison; its casts (`arts`), statuses (`statuses`) and Paralyze guard ride along in the battle's `stacks_json` / `defender_json`, so a battle resumes exactly after a restart. `stepBattleRound(…, battleSeed)` casts before the blows (garrison first, then stacks by arrival), folds statuses into `ArmySide.artMods` and Instinct stats into `ArmySide.kitStats` (both multiply in `strike` / `sideUnit` only when present, so a side without a kit fights bit for bit as before), ticks damage over time after the blows, and reports every happening as `BattleRound.arts` (`BattleArtEvent`: the report's rounds, the battle log through `artEventLine`, the map's floating text and spell effects) and the statuses that held on each side before they counted down as `BattleRound.statuses` (the spell effects' aftermath).
* **Spell effects are data on one kit.** A cast's look is picked by its `fx` id from `SPELL_LOOKS` (spellFx.ts), one option per stage, and `SpellFxStore` writes it once into a ring of GPU particles that the shader moves from a single clock: no per-cast meshes, one draw for every cast on screen. The client never decides what was cast; it plays `BattleRound.arts` and `BattleRound.statuses` as the poll brings each round, in step with the floating names. A boss's battle cry goes through `BOSS_CRIES` (bossCries.ts, NPC id → when), read every frame by `BossModel` and `RigPlayer` (`BossLive.cryAt`), never through React state; a mob's or bandit pack's strike and cast pose through `NPC_STRIKES` (npcStrikes.ts), a uniform list of at most 8 battles that the NPC batch's vertex shader matches to each creature's pack key, so a fighting pack costs no draw, no mesh and no re-upload. A pack's kit is a `UnitKit` on its garrison like a boss's (never `boss`), and its HP and ATK come trimmed by what the kit is worth (`npcKitWorth`), so `sim:balance` can fight every pack with and without its kit on the same seeds. The tie-break roll is a hash of battle id + unit + round, never the battle's rng, so adding Arts never shifts the rolls of the blows. A rally's stacks carry `maxRounds` (`COMBAT.RALLY_MAX_ROUNDS`) and the war engine's exhaustion check and `act_until` use it; heals (`healed`) give soldiers back to their rulers' populations (`applyArtHeals`). A boss's HP carries over between battles, so its `ArtsState.carryAtStart` records the damage it began the battle with: its heals and its *own losses* conditions count only this battle's (`lostThisBattle`), while a last-stand Finale reads its whole HP.
* **A champion is a kit and a stat share on a stack, at a hero's share.** A march it leads carries `champion_json`; `openingStack` gives its stack the champion's `kit` (`championKit` at its level), `artShare` (`CHAMPION_ART_SHARE`) and `champion` (its stat shares), and `attachRulerBuffs` refreshes them every round by the target's `CHAMPION_TARGET_SHARE` (a frontier gate, an epic pack) and puts a fit champion at home on the defending ruler's garrison (`championLed` keeps it for the report). In `combat.ts` any kit bearer's `artShare` scales its strikes, damage-over-time ticks, status values, heals, stat Instincts, Enrage and Cull, and `sideUnit` multiplies the champion's stat shares after the Armory gear. Where a champion is needs no bookkeeping: it is away while `march_id` points at a march still out, so a march home or lost frees it. A wiped stack or garrison wounds it (`woundChampion`); `settleChampions` hands out Renown when the battle ends and adds `championRenown` / `defenderChampion` to the report. On the HD map `BandMarches` walks it ahead of its soldiers in the bosses' `BossBatch`, its rig built from its model key, so champions cost the map no new draw.
* **Armory sets are gear on a stack, read fresh every round.** A march in a set carries `armory_json` (`{ rarity, civ, name, emblem, count }`): `takeSets` takes one set per soldier from `kingdom_armory` as it sets off, `openingStack` marks the stack with its `armory`, and `attachRulerBuffs` attaches its `gear` (`gearOf` × `ARMORY_TARGET_SHARE` against a boss or a gate; dropped once upkeep has rusted it) and the defending ruler's home garrison's (`garrisonGear`: the sets at home, best first, blended by the share wearing each). `combat.ts` multiplies a side's HP / ATK / DEF by the gear on top of civ buffs and titles (`sideUnit`) and adds its edge to the civ trait (`sideTraits`); NPC units and bands ignore it. Survivors put `min(count, survivors)` back in the armory when the march is home; stock is by rarity, so a civilization change reforges it as the new civilization's sets. On the map an armed march draws its soldiers as `soldier1` / `soldier2` / `soldier3` actor kinds (its civilization's soldier with the set's gear, `armsParts` in `actorTemplates.ts`, `armsHd` in `actorHd.ts`), the shapes the soldiers already use, so no new draw per march.
* **A mercenary band is a march of soldier-equivalents.** A band's march carries `band_id`: the war engine builds its stack with its kit (`mercKitFor`) and a `band` marker, skips its ruler's titles and landmarks, leaves it out of `getDeployedSoldiers` and the population ledger, and writes each round's losses back as strength (`setBandStrength`); `combat.ts` only uses the marker to strike a ruler's soldiers before their bands. Rounds and reports carry the band (`BattleRound.bands`, `armies[].band`) so every view shows its losses as −%. In HD `BandMarches` walks every band's models in one `BossBatch` whose sites are carried on their root bone each frame (`place`), so models cost vertices, never draws.
* **A muster is several ordinary marches with one clock.** `launchMuster` checks the whole muster first (`checkMuster`, which throws a `MusterError` listing every problem), then calls `startMarch` for each march inside one transaction (all or none) with a shared `MusterSlot`: the same `departTime` and `arrivalTime` (the slowest march's road time; today every march of one ruler to one target has the same one) and its `muster_rank` (strongest first by `musterRules.ts` power). `handleArrivedOutboundMarches` reads arrivals `ORDER BY arrival_time, muster_rank`, so rank 0 opens the battle at round 0 and the rest join it with `joinedRound = round + 1 = 1` in the same pass, before round 1 is fought. Holding departures back instead would need a hidden pre-departure phase; walking together keeps every march a normal one (its own slot, recall, survivors). A rally muster is `startRally` with several `armies`: one `rally` lobby march each (rank 0 is the rally's own; recalling another one only walks it home).
* **War is server-side, multi-stack and live.** Combat (`combat.ts`) is a pure seeded simulation; `warConfig.ts` holds every number. Soldiers on a march stay in `users.population` but leave `users.soldiers`, so they can't be mobilised twice; the dead leave the population. Live battles (`battles` table) tick one round every 10 s (`BATTLE_ROUND_MS`), allowing arriving armies to join mid-battle (`phase = 'acting'`), before survivors walk home (`phase = 'returning'`) carrying plunder (`carry_json`) that is credited on `return_time`.
* **Fog of war is applied per request.** The in-memory `kingdoms[]` always holds exact numbers; `/kingdoms`, `/kingdoms/:id`, `/spires`, `/map/roving`, the kingdom ledgers and the march preview strip what the session user may not see and add their latest scout report with its `estimate` (kingdoms get no bands: unknown until scouted; packs and nodes keep bands). Not signed in = fog over everything but Special Overseers.
* **Gathering is a march phase.** A `gather` march at its node sits in `phase = 'acting'` with `gather_json` (node mix, amount, rate, start, pause); the node row in `world_npc_state` names it (`gathered_by`) so the node is exclusive. The war tick finishes work at `act_until`; an attack on exposed workers is an ordinary live battle at the node whose defender is that march (its losses come out of the owner's population) and which pauses the work.
* **World bosses and NPC kingdoms.** A boss defends as one unit (`count` 1, its lost HP share in `carryDamageTaken`), with its Battle Arts kit (`bossKitFor`: Instincts Cleave / Enrage, the Art Ward) run inside `stepBattleRound`; `attachRulerBuffs` sets each attacking stack's `damageMult` to `bossHideMult(City Hall)` (Colossus Hide, warConfig.ts, mirrored in `src/utils/war.ts`); its HP and every army's damage are written each round. NPC kingdoms (the buffer realms and the four frontier gates `npc-gate-*`, civ from `NPC_GATE_CIV`; `planMarch` refuses attacks and rallies on a gate by its own civilization, mirrored in `src/utils/war.ts` for the target panel) are rows in `npc_kingdoms` created on first sight; they fight like a fortified castle of their donor civ and regrow in `harvestNpcKingdoms`. Gates use the fixed `GATE` config instead (warConfig.ts, mirrored in `src/utils/war.ts`; an old random-level gate row is reset to it once in `getNpcKingdom`): reinforcements of their civ station there (`reinforceRoomAt` uses the gate's cap) and defend as groups, `chargeGateDuty` bills them each harvest, and `planMarch` refuses attacks on a city whose civ's gate isn't burning (`sealingGate`). The gate's `NpcKingdomStatus.gate` (`sealed`, `catchChance`) is public. Special Overseers are users reset by `resetOverseers` (startup + every harvest); their Resolve is a `statMult` on the home garrison. Boss stats come from `activeBossUnit` (its unit × Vengeance, `vengefulBossUnit` in warConfig.ts); the active boss is `base index + weeks + kills` into the zone's pool (`withActiveBoss`; `boss_rotation.kills` counts a kill only once the fallen boss would wake), and a fallen boss's status carries `next` (`withActiveBoss` at its wake time: the respawn, or the weekly rotation if sooner). The client swaps the rotated boss into the cached map with a key of identity + alive + next only (a fallen zone wears the next boss with `slumberUntil` and `fallenName` and is drawn as a phantom); boss, mob / bandit and resource node ground rings are HP bars through a per-instance `aFill` attribute (boss statuses; `pack.health` on `/map/roving`; node `left` in `nodes`), so HP changes never rebuild the world; a timer refetches `/map/roving` when the next boss wakes. Bosses and legendary sites (legendary nodes, the Relic Hoard, the Nethergarde Core) are rigs (bossRigs.ts → BossModel; in HD the legendary sites and the Core are batched heroes instead); the provinces' legendary landmarks are Builder models (legendaryLandmarks.ts) placed by `generatePersistentBufferNPCs` at each mortal province's centre (`legend-<civ>`, `LEGENDARY_LANDMARKS` with an optional nudge; castles keep `LEGENDARY_CASTLE_GAP` = 12 from them through `keepoutOf` in `plotRules`): about one draw call per bone plus two or three for effects (a legendary site adds a light beam); a legendary chest is left out of the shared NPC batch and drawn by its MapNPC3D; armies fighting a boss (acting marches) make it face their origin and strike; nothing on a boss casts shadows (the shadow map is drawn once).
* **Shared world NPCs.** Roving spawns stay generated (seeded per roving window of `SYNC_INTERVAL_MINUTES × 2`, `rovingWindowMinutes()` in worldMapGenerator.ts, also sent as `/status.rovingWindowMinutes`); only what changed is stored in `world_npc_state` (units left, `dead_until`). The race rule turns other outbound marches around from their interpolated position. `/status.rovingKey` includes a world-state counter and the viewer's newest scout report, so clients refetch the roving list when a pack is hit or killed or the fog lifts.
* **Titles are cached, not computed per request.** `titles.ts` aggregates commits, battle reports and the ledger into `user_earned_titles`: everyone on each Live Sync (`recalculateAllTitles`, ~15 ms for 39 rulers) and per ruler after each saved battle report and returning gather haul (`recalculateTitlesFor`, ~0.3 ms, reusing the commit totals of the last sync). `getAllKingdomsFromDB` reads the cache into `earnedTitles` / `titleBuffs`, so war ticks never run the aggregations. Building levels are not stored: every realm build (each Live Sync, startup and most actions) recalculates each repo's level from all its XP. `getAllKingdomsFromDB` saves each ruler's count of built repos at Lv 3+ in `users.repo_holdings`; when that count changes, `rebuildRealmWithTitles` (Live Sync, startup, admin commit re-check) re-evaluates titles and builds the realm once more, so a new holding counts in the same sync. Before each live round `attachRulerBuffs` (warEngine.ts) puts the owners' cached title buffs plus their Dragon Statue / Mana Spire / Plaza Fountain bonuses on attacking stacks, reinforcement groups and the defending ruler's garrison; `sideUnit` → `effectiveUnit(civ, opp, role, titleBuffs)` multiplies them into HP / ATK / DEF.
* **Improvement bonuses are derived, not stored.** `kingdom_upgrades` only holds tiers; `improvementEffects(upgrades)` (upgrades.ts) turns them into multipliers wherever they apply: `planMarch` / `travelMsFor` (roads, lanterns), `startGathering` / gather preview (market), `getAllKingdomsFromDB` march capacity (banners), `launchDueRallies` (leader's banners), `simulateDemographicCycle` (gardens) and `attachRulerBuffs` before every live round (dragon / spire / fountain, added to title buffs). Special Overseers count as fully upgraded (`getEffectiveUpgrades`, `MAXED_UPGRADES`).
* **Polls never replace unchanged state.** `useGameState` keeps the last response body of `/kingdoms`, `/kingdoms/:id`, `/map`, `/map/roving`, `/spires`, `/marches`, `/battle-reports` and the other polled lists and only sets state when the text changed (direct updates from an action reset the check). `/status` changes on every poll (its sync countdown), so the app re-renders every 3 s; the 3D view is memoised behind `Scene3D` and doesn't re-render with it.
* **One notice system.** Everything that should reach a player once goes through `broadcasts.ts`: a `realm_events` row (the log the realm keeps of itself) and a `broadcasts` row addressed to everyone, a civilization or listed rulers. Reads live on the server, so a notice opens once per kingdom, not once per browser. `/status.noticeKey` tells clients when to refetch; public notices are also written to the Chronicle activity log (`setNoticeLogger`).
* **Royal Decrees are data, read where they apply.** `kingdom_shields` and `kingdom_punishments` hold one row per kingdom with `ends_at`; nothing runs when they expire. `getAllKingdomsFromDB` attaches the active ones (`shield`, `punishment`, public and never fogged), `planMarch` and the war tick's arrival step refuse or turn back marches on a shielded kingdom, `startMarch` / `startRally` / `joinRally` call `breakShieldOnAttack`, and `executeResourceAllocation` leaves punished kingdoms out of the split and scales their births / deaths (`deathMult` in `simulateDemographicCycle`). Decree routes call `refreshInMemoryRealm`, so the realm signature changes and clients refetch; the client also hides a shield or punishment once its `endsAt` passes. Each decree is a `realm_events` row (`decree_*`, `shield_broken`), which is the audit.
* **The weekly story reads the logs, it never keeps its own.** `chronicleDetectors.ts` holds one small function per kind of happening; each reads `realm_events`, `battle_reports`, the ledgers, titles, swaps and deeds for one Sunday-to-Sunday UTC week and returns facts told as legend with a weight. A new system adds its story by writing a detector and listing it in `DETECTORS` (and, when nothing in the logs says what happened, recording a `realm_events` row where it happens, as `rare_find` in warEngine.ts). Commits and lines are only ever told through `realmLabour`'s per-civilization phrases. The story stays plain text with tags (`chronicleMarks.ts`); the client draws them (`src/utils/chronicleMarks.tsx`, one icon per key, mirroring the server's list) and drops any it doesn't know, so a story never shows raw tags. The server never calls an LLM: the admin copies the prompt, pastes the reply back and publishes; the published stories feed the next prompt.
* **Royal Proclamations are timestamps.** `proclamations` keeps when each ruler last called settlers, declared a Festival and attacked a ruler's city or a frontier gate (`startMarch` / `startRally` / `joinRally` call `markCallToArms`); everything else (cooldowns, the Festival's end, the hour of Call to Arms) is derived from them, and nothing runs when they expire. `getAllKingdomsFromDB` attaches `proclamations`, and `GET /kingdoms` and `/kingdoms/:id` overlay a fresh read, since they change between realm builds. `executeResourceAllocation` doubles births and adds 10% to the workforce of kingdoms in a Festival (`festivalUserIds`). The city draws the Festival from `cityFestival` in `blueprints.ts` (its own `InstancedParts` batch, through the HD model kit in HD, and townsfolk added to the actors) plus `Fireworks`; the world map adds `Fireworks` over each festival castle.
* **Epic landmark rotation.** Each buffer region shows `EPICS_PER_REGION` (1) of its pool of 6 epic landmarks (`BUFFER_POOLS[…].terrains`, ids `terrain-<zone>-<design>`). `world_map.json` keeps `landmarks: { week, rotations }`: `settleEpicLandmarks` upgrades an older saved map in place (keeps the standing one, renames the old `shipwreck` to `lm-shipwreck`, drops extras, finished), `rotateWeekly` rotates every region on the first load in a new week (rotation day = Sunday 00:00 UTC → +24 h) and `resetLandmarks` (admin) rotates now. A rotation stores the arriving ids and the leaving NPCs; `landmarksAt` serves them as `landmarkState: { phase: 'rising' | 'crumbling', from, until }` while the day lasts. `placeEpic` samples the region with per-blocker gaps (16 landmarks, 14 castles / bosses / kingdoms / gates / the day's nodes, 6 walls) and falls back to the spot falling least short. Daily resource nodes keep to the landmarks as they stood at 00:00 UTC (`nodeBlockers`), so a mid-day reset never moves them. On the client the map turns `landmarkState` into a `landmarkStep` (0–9, checked once a minute) so `buildNPCModel` → `stageLandmark` rebuilds the model and the static shadows only 10 times a day; NpcLife adds masons / shapers at rising sites and onlookers at crumbling ones.
* **Buffer realm cycle.** Each zone's NPC kingdom (`BUFFER_POOLS[…].kingdoms`, 3 per zone) runs a 28-day cycle from the clock: `realmClock` counts weeks from a Sunday, zones a week apart, so the stage (common → epic) and day are derived, never stored; `realmLevelOn` (warConfig) gives the City Hall. `world_map.json` keeps `realms: { [zone]: { cycle, leaving? } }`: `cycleRealms` swaps in a new realm (id `kingdom-<zone>-<cycle>`, so its `npc_kingdoms` row starts fresh) when the cycle rolls over and keeps the old one crumbling for a day (an admin move drops it at once; `pruneNpcKingdoms` deletes the rows of realms no longer on the map, each harvest and after a move); `realmsAt` stamps `realm` (stage, day, level, building), the stage's rarity and a rising `landmarkState` on building days into the served map. `getNpcKingdom` rebuilds a realm to full whenever `realm.level` differs from its row; `planMarch` and `openNpcKingdomBattle` refuse / turn back marches while it carries a `landmarkState` (shield). `landmarkKey` includes realms' stage and level so clients refetch the map on each change.
* **Castle placement.** `placeKingdoms` (worldMapGenerator.ts) is the one placement routine: candidate plots from `castlePlotCandidates`, a jittered scatter over the province seeded by the province (mortal provinces ranked by distance from the centre plus noise, the Voidrift in random order), kept ≥ 8 from other castles, 6 from fixed landmarks, `WALL_CASTLE_GAP` (4.5) from the gates' border walls (`gateWallPoints`, also blockers for resource nodes and roving spawns) and 12 from a province's legendary landmark, and with an Archon ≥ `ARCHON_SEAT_CLEARANCE` (14) from the seat and out of the strip behind it. Every map load re-checks saved spots (valid ones stay, so nothing moves without reason; bumping `CASTLE_LAYOUT_VERSION` lays every castle out afresh once); `freeCastlePlots` gives the open Voidrift slots plots by the same rules; `relayoutKingdomPlacements` lays everything out from scratch.
* **Admin World Rebalancing.** Authorized administrators (`ADMIN_USERS`) can trigger `POST /api/admin/reset-world` to rebalance all civilizations, wipe saved `kingdom_layout` plot plans, and regenerate the world map.

## SQLite Schema (db.ts)

Each module creates its tables with `CREATE TABLE IF NOT EXISTS` holding every column; there are no `ALTER TABLE` migrations. A column added later reaches only a fresh `realm.db`, so an existing database needs the column added by hand (or the file reset).

| Table | Purpose |
|---|---|
| `users` | Git users + chosen civilization + wall state (`wall_hp`, `wall_updated_at`) |
| `user_emails` | Every known email → user (primary, secondary, learned from commits, assigned by an admin) |

| `repositories` | Repos from Git (`backfilled_at` = historical backfill checkpoint) |

| `commits` | Commits with line stats, resolved author and `meaningful_lines` (from the diff, NULL until analysed) |
| `pull_requests`, `pull_reviews` | PRs and reviews for XP |

| `population_ledger` | Census: births, deaths, (de)mobilisation, battle losses, civ swaps |

| `rallies` | Rallies (leader, civilization, target, `launch_at`, `joiner_cap`, `status`: `open` / `launched` / `cancelled`) — warEngine.ts |
| `battles` | Live multi-stack battles at a target (`round`, `next_round_at`, `stacks_json`, `defenders_json`, `rounds_json`, `status`) — warEngine.ts |
| `battle_reports` | Every battle, full report in `details_json` (`defenderNpc` for mob / bandit fights, `armies` per stack / reinforcement), `participants` (`,id,id,` — every ruler who fought, so all get the report) — warEngine.ts |

| `boss_rotation` | Kills per boss zone (`kills`): each one moves the zone's rotation pool on one boss; `week_key` + `week_kills`: kills this week = Vengeance stacks (+10% HP / ATK / DEF each, `BOSS_VENGEANCE_PER_KILL`), 0 after the weekly rotation — worldNpcs.ts |
| `boss_damage` | Damage per ruler against a boss in one life (`npc_id`, `life_key`, `user_id`) — the bounty is shared by it — worldNpcs.ts |
| `npc_kingdoms` | Simulated NPC kingdoms (buffer realms, gates): `level`, donor `civ`, `population`, `garrison`, `treasury_json`, wall HP, last attack, `hoard_claimed_at` (a free realm's conquest hoard, once a day) — worldNpcs.ts |

## Navigation

* **Login screen** — `AuthGate` shows `LoginScreen` to every signed-out visitor (black until `/auth/me` answers) and mounts `App` only for a signed-in ruler, or for a visitor who chose *Look around without signing in* when the server has `GUEST_BROWSING=true`. Signing out reloads the page back to the login screen. The server enforces the same rule: past `/api/auth/*` every route answers 401 without a valid session unless `GUEST_BROWSING=true`; the one public data route is `GET /api/login/realm`, the login flyover's realm with every name left out.
* **`world_map`** — `FlatWorldMap3D`; click a castle → `city_view` for that kingdom.
* **`city_view`** — `CityView3D`; click a building → `BuildingModal`, click the town hall → `DevProfileModal`.
* The last view is persisted in the browser so a reload returns to it.
